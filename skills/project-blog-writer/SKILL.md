# 项目博客写作

把真实项目记录写成读者可以照着操作、也能理解取舍的中文文章。适合学生开发者的实践口吻：直接、具体，有疑问和判断，不虚构个人经历。

## 从记录确定一条主线

先读取用户指定的会话、代码或日志，确认文章主题、读者和目标。优先沿用已有博客目录、格式与网站。信息不足时，先写能证实的部分，只询问影响结论的缺失信息。

从记录中找出「要解决什么 → 实际怎么做 → 遇到什么问题 → 如何验证」的主线。选择有价值的细节，不把整段聊天或每次尝试搬进文章。区分历史实验快照和现在的环境，明确示例代码、计划步骤与已经完成的操作。

涉及数字、费用、准确率或性能时核对原始证据，写清日期、单位、样本量与统计范围。不把测试通过当成效果提升，不把模型生成的回答当成已审核训练数据。没有测量就不编百分比。

## 撰写实用正文

先说明实际问题和读完能完成的事，再展开关键步骤。按主题选择结构，不强制每篇使用相同章节。使用必要的命令、目录、字段映射和小例子，让读者知道在哪里执行、应看到什么结果。

代码与项目自定义脚本要说明前提；不要把自定义脚本写成官方命令。会变化的工具参数、安装方法和版本行为，按当前可用的官方资料核实，引用直接支持结论的页面。

保留两三个真正影响结果的坑和取舍，用「现象、原因、改法、验证」讲清楚。只在流程或组件关系不易用文字解释时添加图。少用口号、夸张标题和万能结论，不给普通操作堆砌高级术语。

发布前移除 API 密钥、密码、私人服务器地址及未获授权公开的个人信息。示例使用明显占位符。涉及来源材料时以自己的叙述为主，保留必要来源链接，不复制大段第三方文章。

## 检查与交付

复核关键事实、数字、链接、代码前提及「已完成／待完成」界限。交付正文或按用户指定位置保存；若用户要求发布，读取 [发布与核对](references/publishing.md)，完成现有授权内的发布并实际检查页面。未要求发布时不要推送或公开内容。
